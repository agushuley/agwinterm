# Menu bar in the title bar — agterm's menus, in agwinterm's chrome

agwinterm only. agterm's menu bar is the macOS system bar (`agterm/agtermApp+Menus.swift`); on
Windows the equivalent surface is the custom-drawn title bar, so the menu bar becomes a row of
labels in it — **File  View  Navigate  Help** — and each label drops a themed menu (the popup
`Menu.cs` already draws for context menus). The items are agterm's, in agterm's order and wording,
except where the Mac word has a Windows word (Finder → Explorer, ghostty.conf → agwinterm.conf) and
where agterm's item has no agwinterm counterpart (listed at the end; omitted, not invented).

## What the user gets

- A menu bar after the sidebar toggle, before the title: `File  View  Navigate  Help`, drawn in
  `_uiFont` on `ChromeBg`, hover-highlighted like the chrome buttons. Normal (40 px) and compact
  (30 px) toolbar modes both show it; the hidden mode shows no chrome and so no menu bar.
- Click a label to open its menu; while one is open, moving over another label switches to it;
  click outside, Esc, or running an item closes it. Items show their **effective** shortcut from the
  keymap (a rebound chord shows the rebind), a disabled item is dimmed and inert, a state item's
  label tracks state (Hide/Show Sidebar, Flag/Unflag Session, Show Flagged/All Sessions,
  Focus/Unfocus Workspace, Collapse/Expand Workspace, Show/Hide Scratch, Focus Left/Top Pane).
- Keyboard: a bare **Alt** tap (press and release with no other key) or **F10** focuses the menu bar
  (File highlighted); ←/→ move between labels, ↓/Enter opens, Esc leaves. **Alt+F / Alt+V / Alt+N /
  Alt+H** open a menu directly. Inside an open menu ↑/↓ move, ←/→ switch menus, Enter runs, Esc
  closes — the native Windows model. A lone Alt tap sends nothing to the shell that the shell was
  not already getting (win32-input-mode sees the modifier down/up as today).
- Submenus: **File ▸ Open Window** (the window library, a check mark on open windows) and **File ▸
  Open Recent** (closed sessions, closed workspaces, Clear Menu) open a flyout to the right of the
  row on hover or →.
- Accessibility: the menu bar is a UIA **MenuBar** with **MenuItem** children (Expand/Collapse,
  Invoke); an open menu's rows are MenuItems too, so Narrator/NVDA read and run them. F1 help lists
  the mnemonics.
- Settings ▸ Interface: **Show menu bar** (`show-menu-bar = true`), off hides it; Alt/F10 do
  nothing then. `agwintermctl config get/set show-menu-bar` follows.

## Enablement, one predicate

agterm's rule: one predicate per item, read by the menu, the palette and a keymap alternative alike,
so they cannot drift. agwinterm's palette has no enablement today (every row runs). This batch adds
`Func<bool>? Enabled` to `PalItem`, evaluated when the menu opens and again on Enter/click; the
terms are the same as agterm's: a modal cover (dashboard, palette, rename field, native picker),
no active session, no current workspace, one window left (Delete Window), no flags (Show Flagged),
flagged mode (Expand/Collapse Workspaces), one pane (Swap Panes, Focus *). The palette reads the
same predicate and renders inert rows dim; a disabled row neither runs nor dismisses.

## Where the code goes

- `src/Agwinterm.Core/MenuModel.cs` (new, host-free): the four menus as data — label, action name
  or a `MenuCommand` id, mnemonic, `Enabled` term names, state-label pairs, submenu kind. Unit-tested
  (`Agwinterm.Core.Tests/MenuModelTests`): every agterm item is present in order, mnemonics are
  unique within a menu, every action name is in `Keymap.ValidActions`.
- `src/Agwinterm.Win32/MenuBar.cs` (new): layout (label rects in the title bar), hit-testing,
  hover, the Alt/F10 state machine, opening a dropdown through `Menu.cs`, keyboard routing while
  open, flyouts (a second popup for a submenu, closed with its parent).
- `Menu.cs`: disabled rows, check marks, submenu arrows, a shortcut column from the keymap, ←/→
  switch to the neighbouring menu when opened from the bar.
- `Program.Services.cs` `DrawTitleBar`: the label row after the toggle; the title budget shrinks by it.
- `Program.WndProc.cs` / `Program.Input.cs`: Alt tap, F10, Alt+mnemonic, key routing to the open menu.
- `Uia.Tree.cs`: MenuBar + MenuItem nodes (Expand/Collapse + Invoke), open-menu rows as MenuItems.
- `TerminalConfig.cs` + `Settings.cs`: `show-menu-bar`; `config` verb key.
- Docs: `docs/user-guide.md` (menu bar, keys), README "What it does" one clause; the skill gains
  nothing (the API is unchanged).

## Decisions taken while building (2026-09-16)

- Settings has no Interface tab (the `show-*-button` keys are config-file only), so `show-menu-bar`
  is a config key and a `config` verb key, not a Settings row.
- The focus-set items (Add Workspace to Focus / Toggle Workspace Filter / Clear Focus) are omitted:
  `WorkspaceFocusOp` is one workspace, on/off/toggle.
- Alt+mnemonic is read in the window procedure off the WM_SYSKEYDOWN context bit, not in
  OnKeyDown off GetKeyState, so a posted key (the test) and a typed key take the same path; a
  keymap.conf chord on the same Alt+letter wins (the dispatch runs first), which is how a shell keeps
  Alt+F.
- The OS's SC_KEYMENU (the invisible menu mode a lone Alt used to enter) is swallowed; Alt+Space
  still reaches the system menu.
- Rename Window… reuses the sidebar's inline EDIT, placed over the title text.
- About is a native message box (version, commit, link); Developer Documentation opens
  docs/control-api.md on GitHub.
- The palette honours the same `Enabled` predicate a menu row carries (dim + inert), but the Actions
  palette's own rows are not yet given predicates — a follow-up, not part of this batch.

- The suite is `tests/integration/menu-bar-ui-cases.ps1` under `hud-ui -Suite Menu` (not a
  `menu-bar.ps1`); it drives the bar through UIA, posted keys and a posted press on the popup —
  never global input. Alt+V is the mnemonic case (Alt+F would collide with nothing, Alt+H is the
  keymap-wins case).
- UIA exposes Invoke on the labels and rows (no ExpandCollapse); rows carry IsEnabled and
  AcceleratorKey; row identities name their menu.
- The dashboard is NOT a modal term: the bar works over it, as the keyboard does.
- Rows have no mnemonics of their own (agterm's don't); only the four menus do.
- F10 focuses the bar unless the pane is a full-screen program (alternate screen or mouse
  reporting), which keeps its F10 as it does in Windows Terminal; Alt still reaches the bar.
- Reveal in Explorer selects the directory in its parent (`explorer.exe /select,`).
- Reload Config applies, for every key whose value differs from the value last APPLIED (a record
  `config set` maintains — it re-reads the whole file but applies one key), exactly the steps
  `config set` applies (`ApplyConfigKeys`), the quick-terminal hotkey registered first; a refused
  hotkey stays out of the applied record (the next reload retries) and every step's note lands in
  the one reload toast.
- A char-making key the menu owns is decided BEFORE its key-down runs: a row that pumps a modal
  loop (About, a close confirmation) would otherwise hand the queued WM_CHAR to the pane.
- Found and fixed on the way: `Uia.RaiseFocus` handed the core a fragment pointer where an
  `IRawElementProviderSimple*` is expected, wedging the UI thread when a focusable element was
  invoked with a client attached (the core sets focus first). Sidebar rows were exposed to it too.
